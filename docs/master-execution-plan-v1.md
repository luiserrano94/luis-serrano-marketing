# LUIS SERRANO — MASTER EXECUTION PLAN V1

## Purpose

This document is the single source of truth for the next version of the Luis Serrano website and its surrounding acquisition, content, email, analytics, commercial, print and automation systems.

Do not make strategic assumptions that contradict this document.

The goal is not simply to build a portfolio website. The website must operate as the central owned platform for three connected systems:

1. **Creative work and commercial services**
2. **Fine-art print commerce**
3. **Educational Resources and audience acquisition**

These systems must coexist without diluting the core identity of the brand.

---

# 1. BRAND POSITIONING

## Public brand

The public-facing brand is:

**Luis Serrano**

Do not use:

- Luis Serrano AI
- Luis Serrano MKT
- AI Artist as the primary identity
- AI Creator as the primary identity

## Primary positioning

Luis Serrano should be perceived first as a:

**Creative Director / Visual Artist**

AI and technology are part of the practice and production system, but they are not the entire identity.

The site must never feel like:

> An AI tutorial creator who also makes images.

It should feel like:

> A creative director and visual artist with strong visual taste who also understands and shares the technology behind his work.

## Core hierarchy

The site should preserve this hierarchy:

**Work → Commerce → Knowledge**

Or conceptually:

**Work**  
This is what I create.

**Services**  
This is how you can work with me or acquire the work.

**Resources**  
This is what I know and share.

**About**  
This is who I am.

Resources may eventually become one of the largest traffic and lead-generation engines on the site, but they must never visually dominate the Luis Serrano brand.

# 25. WHAT SHOULD BE EMAIL-GATED

Gate content when the user can meaningfully **do something** with it or when Luis has added substantial work/curation.

Gate:

- Installation guides
- Curated repo collections
- Configurations
- Templates
- Complete prompts
- Workflows
- Playbooks
- Checklists
- Starter kits
- Downloadable files
- Deep comparisons
- Research that meaningfully saves time

Do not gate:

- Opinions
- Hot takes
- Simple tips
- Basic news
- Quick discoveries
- Individual public recommendations
- Surface-level comparisons
- Behind-the-scenes
- Basic creative-process commentary

## Core ethical/content principle

Never gate a public link simply to collect an email.

Bad:

> Give me your email and I'll tell you the name of this public GitHub repo.

Good:

> The repo is OpenMemory. Here is what it does. If you want my installation, configuration and real workflow, unlock the full guide.

The email exchange is for **Luis's added value**, not artificially hidden public information.

# 27. RESOURCE GATE

Example route:

`/resources/openmemory`

Before authentication/unlock, user may see:

- Title
- Description
- Category
- What the Resource includes

But not the full body.

Display:

**Unlock this Resource**

Email input

**Unlock**

## Required behavior

No email:

**No full content**

Valid email:

1. Email submitted
2. Contact registered/updated
3. Access granted
4. Gate disappears
5. Full Resource loads
6. User remains on same URL

Do not:

- Redirect to Gmail
- Require inbox confirmation to read
- Force PDF download
- Redirect to an external landing page

Unlock occurs immediately on-site.

---

# 28. GATE IMPLEMENTATION

The gate must be functional, not merely visual.

Do not render the full Resource body in client HTML and hide it with blur/overlay.

Unauthenticated requests should not receive the complete body.

After access validation, the server can deliver the full Resource.

---

# 29. RETURNING RESOURCE USERS

A visitor should only provide their email once per device/browser under normal conditions.

After first unlock:

**Entire Resources library becomes accessible.**

Do not require email again for every Resource.

Use a secure first-party mechanism such as a signed cookie.

Suggested duration:

**365 days**

Do not store raw email in localStorage.

Do not build:

- User accounts
- Passwords
- Login
- Password recovery
- Profile dashboard

Those are unnecessary in V1.

If a visitor clears cookies or changes devices, they may encounter the gate again. Entering the same email should update the existing subscriber rather than create a duplicate.
